# X8 SE official hub DPI block reconstruction

## Scope and safety

This note documents a static reconstruction of the 60-byte X8 SE DPI settings
block built by the official ATTACK SHARK HUB web application. The Rust module
`src/x8se_official_hub.rs` encodes that block in memory for offline testing.
It does not open HID handles, send reports, or implement the browser's local
WebSocket helper protocol.

The result is not ready to send to a mouse. No physical X8 SE HID write capture
has verified report ID, report length, transport framing, response behavior,
device acceptance, readback, or persistence. Do not connect this encoder to the
existing HID probe until those details are captured and checked.

## Static source inspected

On 2026-10-16, the official hub's deployed JavaScript was fetched as text and
inspected without executing the application:

| `https://szslxd-tech.com/assets/dpiX8SE-Bh7olmqY.js` | `661f26a4a60f5693153761606e1dabb11eeebe36fae9dc5b3a4954baba0fd5b7` |

The X8 SE UI module imports the main bundle's `bi` export, which resolves to
the serializer function `To`. The UI maps X8SE to device ID `0x02`; on a stage
change it passes the eight DPI values and the one-based active stage to the
serializer, prefixes the resulting bytes with the selected connection method
and model ID, hex-encodes the message, and sends it through its local WebSocket
helper. This establishes the application's message construction and send
attempt, not the final HID report sent by the native helper.

The default UI values are `800, 1600, 2400, 3200, 8000, 25000, 0, 0`, with
stage 2 active. The sliders show a minimum of 50, maximum of 25,000, and a step
of 50 below 10,000 or 100 at/above 10,000. These are UI settings, not verified
hardware limits.

## Reconstructed 60-byte layout

Offsets below are zero-based. All values are emitted by the JavaScript
serializer into a zero-initialized `ArrayBuffer(60)`.

| Offset | Length | Meaning |
| --- | ---: | --- |
| 0 | 1 | Fixed marker: `4` |
| 1 | 1 | Declared data size: `56` |
| 2 | 1 | Profile ID; observed default `1` |
| 3 | 1 | X sensitivity parameter |
| 4 | 1 | Y sensitivity parameter |
| 5 | 1 | Enabled-stage flags; observed default `0x3f` |
| 6 | 1 | X double-range flags, calculated per DPI stage |
| 7 | 1 | Y double-range flags, calculated per DPI stage |
| 8–15 | 8 | Encoded X DPI slot bytes, stages 1–8 |
| 16–23 | 8 | Encoded Y DPI slot bytes, stages 1–8 |
| 24 | 1 | Active stage, one-based |
| 25–48 | 24 | Eight 3-byte DPI indicator colors |
| 49 | 1 | DPI indication type; observed default `2` |
| 50–51 | 2 | Additive checksum, high byte then low byte |
| 52–59 | 8 | Zero padding |

The checksum is the sum of bytes at offsets 3 through 49 inclusive, stored
big-endian. The first indicator loop in the deployed serializer contains the
expression `n+++d` (JavaScript parses it as `n++ + d`). The encoder mirrors the
resulting gap/overwrite at offsets 26 and 29 rather than silently correcting
the vendor output. A real capture should confirm whether the deployed hub
continues to emit these bytes.

## DPI value encoding

The bundle uses a 220-entry lookup array named `mo` (the source calls it
`DPI_3311` in an error message). The Rust table is copied from that bundle.
For nonzero DPI values, the serializer first maps high ranges as follows:

- `12,001..=24,000`: round DPI / 2 and set the corresponding X double flag.
- `24,100..=25,000`: round DPI / 3, clamp to 8,000–8,500, and set the Y double flag.
- Other values above 24,000 map internally to 8,500, although those values are
  not reachable through the observed slider increments.
- Values at or below 10,000 are rounded to a 50-DPI table step; larger
  transformed values are rounded to a 100-DPI table step with a 10,100 minimum.

The encoded slot contains the lookup-table byte and a second byte of `0` or
`1`. A zero DPI value becomes `[0, 0]`. The Rust API rejects values outside
the observed slider increments instead of silently normalizing them. This is
a transcription of UI logic, not a statement that the mouse accepts every
value.

## Offline reference vector

`encodes_official_hub_default_stage_values` compares the Rust output to this
60-byte vector generated by invoking the extracted deployed JavaScript
serializer with the UI's default stage values. It is a synthetic software
reference, **not** a USB/HID capture:

```text
04380100013f00201225384bbcc40000000000000000000002ff000000ff000000ffffff0000ffffff00ffff4000ffffff020fd10000000000000000
```

Run the pure unit tests with:

```text
cargo test --lib
```

## Next hardware validation

With the physical X8 SE available, first save its current DPI settings and
capture the official hub changing exactly one stage. Record the receiver and
mouse state, selected connection method, outgoing local-helper message,
resulting HID report(s), replies, and before/after readback. Compare the
captured settings block with this encoder, including the checksum and
indicator bytes. Then verify accepted values, unrelated-stage preservation,
standard-user access, and persistence after a power cycle. Do not enable a
setter before that comparison passes.
